# 治理报告 6：残余不足与下一阶段治理方案

> 日期：2026-08（24h 冲刺收官后）
> 依据：阶段总结中"仍存在的不足"清单，逐条系统化——问题本质 → 方案 → 优先级 → 验收
> 目标：把项目从"能写简历、点开不虚"推进到"证据扎实、可靠性有根、可长期演进"

---

## 一、残余不足盘点（已归为 6 类）

| # | 类别 | 核心问题 |
|---|---|---|
| A | **业务有效性证据** | 回测单段 12 月、未计成本/存续偏差、消融与正确性评测"框架就绪但未真跑" |

## 二、方案（逐类：问题本质 / 做法 / 优先级 / 验收）

### A. 业务有效性证据 —— 优先级 P1（1-2 周内）

**A1 回测扩展到多窗口**（P1，半天）
- 现状：仅 2025-07~2026-06 单段。
- 做法：BacktestEngine 已参数化 → 跑 3 个市况窗口（如 2023 熊市段/2024 震荡/2025 上行），输出各窗口绩效合并表。
- 验收：`reports/backtest/` 下多 run_id + 一张"跨窗口"汇总表；报告明确"该策略哪些市况有效、哪些失效"。

**A2 交易成本与存活偏差显式化**（P1，1 天）
- 做法：BacktestEngine 加可选 `cost_bps`（默认 0，设为 10~20bps 各跑一版）；报告增含成本列；对成分股存续偏差加一句"池为 CSI300 当前成分，历史存续偏差存在"（已有文案，补量化说明）。
- 验收：成本敏感性表（0 / 10 / 20bps × 绩效）；把"82.86%"改成"含 15bps 成本后 X%"这样可信的数字。

**A3 消融实跑（小矩阵）**（P1，需 API key，半天跑）
- 做法：R4 runner 就绪 → 用 2 ticker × 3 配置 × 2 重复 = 12 次分析的**最小矩阵**，深/浅模型各一档控成本；`--provider deepseek`。
- 验收：`reports/ablation/<ts>.md` 一张真实表；结论写进 README（"辩论是否提升一致性"有实际数字，无论正负）。

**A4 正确性评测实跑（小集）**（P1，需 key，半天）
- 做法：R10 runner 就绪 → `--n 5` 起跑，先验证 point-in-time（见 A5）再扩到 20。
- 验收：`reports/eval/<ts>.md` 含混淆矩阵 + 方向准确率。

**A5 历史日 point-in-time 验证**（P1,半天，**必须先于 A4**）
- 现状：技术因子已核查；但工具链对历史 `trade_date` 是否只用 ≤当日数据未验证（潜在 lookahead）。
- 做法：审计 `route_to_vendor` 各工具传入 `curr_date` 后底层 fetch 的 end 参数（对齐 technical._load_histories 的做法，强制 end<=trade_date）；不达标处加 cutoff 或标注"该工具仅实时可用"。
- 验收：grep 审计表（工具 → 是否点时间）；报告注明。

### B. 数据可靠性 —— 优先级 P2（随 bug / 1-2 周穿插）

**B1 vendors 类型化（逐链路）**
- 本质：底层 `except: return None` 让 `VendorError` 体系只在上层用、传不上来。
- 做法：**锁定东财/百度两个已知失效源先做**——把 `fetch_fund_flow_em` / `fetch_policy_news_baidu` 的失败改为 `raise VendorUnavailable` 并让上层捕获降级（这是最小闭环、有真实触发点）；其余源随真实 bug 推进，严禁一次性大改。
- 验收：上述 2 源失败时出现类型化异常路径 + 日志；其余维持现状（健康监控已兜底可观测）。

**B2 AkShare 版本漂移防护**
- 做法：`pyproject` 锁 akshare 版本下限（当前可用版）+ `capability.check_libraries` 增加"关键接口存在性"探测（如 `hasattr(ak, "stock_individual_fund_flow_em")` 失败即 WARN，走备源）；把"东财资金流"改用可用替代接口或移除该分支。
- 验收：启动探测能提前 WARN 接口漂移，而不是运行中静默失败。

### C. 端到端验证 —— P1（需 key，半天）⭐ 建议最先做
- 做法：**一条真实分析链 smoke**：`AnalysisRequest.default_for("600519")` → `AnalysisService.run`（真 key）→ 检查：决策非 N/A、confidence 有值/明确 None、报告文件落盘、route_summary 完整。
- 意义：这是"项目真能跑通"的**单人铁证**；R4/R10 实跑也都依赖它先通。
- 验收：一次完整真实分析跑通 + 截图/报告（也是简历演示素材）。

### D. 技术小债 —— P3（低优先，随大版本）
- D1 `cli` → `tradingagents.cli`：全库 import 约 20 处的机械迁移，等下一次大版本一次做。
- D2 config 全局单例收口：`dataflows/config.py` 的 `_config` 改为显式传入（低优先，已不阻塞任何东西）。
- D3 化石改名：`_generate_llm_route_insight` 等改名随碰随改，不动行为。

### E. 作品化 —— P0（24h 内，简历落地的最后一块门面）⭐ 最高优先
- 做法：
  - README 顶部加"技术叙事"区：问题 → 架构 → **回测/敏感性/测试/健康监控数字** → 快速开始 → 架构图。
  - `docs/architecture.md`（分层图 + 决策流程图，png/ASCII）。
  - 把 `sensitivity.md` / 回测 `equity_curve.png` 结果文案搬进 README（凭证，不搬 reports 二进制）。
- 验收：招聘方点开第一屏即看到"回测 82.86%/夏普 2.17/439 测试/供应商健康监控/2890 行大文件拆解"等硬信号；README <10 分钟读完能get故事。

### F. 测试体系偏斜 —— P2（长期）
- 做法：为**关键业务路径**（merger 冲突规则、TechnicalStrategy 评分、回测净值）各补 2-3 个 **golden 真值用例**（已部分有：merger golden、backtest 数学）。
- 验收：业务关键路径的 golden 覆盖 ≥ 关键函数 50%；与 R10 评测集形成"冻结 + 验证"双保险。

## 三、优先级线路图（怎么排）

```
P0（24h 内 · 简历最后一块门面）
  C 端到端真实 smoke（需 key）→ 产演示素材
  E 作品化：README 技术叙事 + 架构图 + 数字外显

P1（1-2 周 · 证据扎实化）
  A5 point-in-time 验证 → A4 正确性小跑 → A3 消融小矩阵（都基于 C）
  A1 多窗口回测 + A2 成本/存续偏差显式化

P2（随 bug / 长期穿插）
  B1 东财/百度类型化（有真实触发点） + B2 AkShare 防漂移
  F 关键路径 golden 补强

P3（随大版本）
  D cli 迁包 / config 收口 / 化石改名
```

**排序理由**：C+E 决定"能当面向别人演示"（24h）；A 决定"数字能不能经得起追问"（1-2 周）；B/D 是工程债，不阻塞但别拖成烂账；F 是防守补强。

## 四、风险与边界（前人栽的坑）

1. **不要把 82.86% 当预测能力宣传**——它是单段、无成本、技术因子 only、存续偏差下的"方法论演示"。每个数字旁必须挂限制句，这是可信度的根基（简历项目尤其如此）。
2. **A3/A4 需要真实 LLM token 预算**——先定预算（如 ≤$5）再定矩阵规模，宁小毋大。
3. **B1 类型化严禁一次性大改**——vendors 全量改 = 无法验证的破坏面；只做"有真实触发点"的 2 源闭环。
4. **先验收再写 README**——README 里的每个数字都必须来自 `reports/` 真实产物，不许手工拍脑袋（重复 R8 的教训：文档失真=信任崩塌）。

## 五、结论

这个项目现在**能写进简历**（有回测引擎、439 测试、重构叙事、消融/评测框架）。缺的不是功能，而是**三样收尾**：
1. **E·门面**（24h）：README 把已有资产"外化"，让人一眼看到分量；
2. **C·铁证**（24h，需 key）：真实跑通一次完整分析，作为演示与后续全部验证的地基；
3. **A·证据**（1-2 周）：多窗口回测 + 成本显式化 + 消融/评测小实跑，把"82.86%"变成"经得起三连问的结论"。

**最优先的一击：C（端到端 smoke）→ E（作品化）→ A5→A4→A3**。做到前两项，简历可贴且点开不虚；做完 A 项，深挖也不虚。
