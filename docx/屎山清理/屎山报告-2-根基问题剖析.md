# 屎山报告 2/3：根基屎在哪里（深度剖析）

> 上一轮体检（`PROJECT_ARCHITECTURE_REVIEW.md`）列了 5 个系统性问题，属于"广度扫描"。
> 本轮换了挖法：**顺着数据流从地基往上读**，每一条都给当前代码的 file:line 证据。
> 结论：这座屎山不是"很多文件写得烂"，而是**七条根基烂在承重墙里**。表层屎（长文件、烂命名）随时能清，根基屎不清，二开加的每个功能都会放大它们。

## 先回答核心问题：根基屎到底是哪里？

按烂的程度和对二开的阻碍排序：

| # | 根基 | 一句话 |
|---|---|---|
| 1 | 状态双写、无 canonical schema | 同一份数据存两套形状，三条路径来回抄，没人知道哪份是真的 |
| 2 | 三个平行的图执行驱动器 | 同一个引擎有三套启动代码，行为已经分叉 |
| 3 | try/except ImportError 静默换引擎 | 你以为在测新代码，实际跑的是旧代码 |
| 4 | 配置双中心 + 全局可变单例 | 图一份配置、数据层一份全局配置，构造时单向同步一次 |
| 5 | 数据层依赖反了 + 四模块环 | 通用层 import 应用层；"供应商"名字是虚构的 |
| 6 | 新旧 CLI 分叉 + 安装入口指向旧引擎 | pip 装完跑的是旧代码 |
| 7 | 吞异常 + 作文注释文化 | 171 处宽泛捕获；360 行文件 40 行代码 |

下面逐条拆解。

## 根基 1：状态双写——最深的那条根

### 现状证据

`AgentState`（`agents/utils/agent_states.py:228-287`）里，**每一类业务数据都有平铺和结构化两种存法**：

| 平铺字段（旧） | 结构化字段（新） |
|---|---|
| `market_report` / `sentiment_report` / `news_report` / `fundamentals_report` | `analyst_reports.market` 等（agent_states.py:250-254） |
| `investment_debate_state` / `risk_debate_state` | `debate_blocks.investment` / `debate_blocks.risk`（agent_states.py:260-264） |
| `investment_plan` / `trader_investment_plan` / `final_trade_decision` | `decision_blocks.*`（agent_states.py:263-279） |
| `company_of_interest` / `trade_date` | `ticker_info.symbol` / `ticker_info.trade_date`（agent_states.py:238-243） |

为了维持两套形状，系统里有**三条同步路径**：

1. **节点写入时双写**：`agents/utils/state_helpers.py:256-339` 的 `sync_report_updates()` / `sync_decision_updates()` / `sync_investment_debate_update()` / `sync_risk_debate_update()`——每个节点的返回值同时写平铺键和结构化键；
2. **图跑完后反向补齐**：`graph/trading_graph.py:282-361` 的 `_synchronize_structured_state()`——图执行结束后，把平铺字段的值**覆盖**回结构化块（注意方向：平铺是权威，结构化是镜像）；
3. **构造时注入**：`propagation.py` 创建初始状态时再填一轮默认值。

### 为什么这是根基屎

- **没有 schema 版本号、没有"谁是权威"的声明**。双写从"迁移期临时手段"变成了永久制度。任何消费者（UI、日志、报告、记忆）想读哪个形状都行——`_log_state()`（trading_graph.py:363-429）甚至**两种形状全写进日志**，一份日志里同一份报告存两遍。
- **方向反了**：结构化块本该是未来，但 `_synchronize_structured_state()` 每次跑完都用旧平铺值覆盖它。也就是说，你未来想"切到结构化、淘汰平铺"，得先拆掉这条反向同步，而它藏在图的执行出口上。
- **魔法数字藏在 helper 里**：`state_helpers.py:351-399` 用**字符串长度阈值**决定执行路径（辩论历史 ≥4000 字符走 `trader_handoff`，manager 决策 ≥2500 走 handoff，交易计划 ≥3200 / 输出 ≥2200 走 `risk_handoff`，风险历史 ≥3500 / 论点 ≥1600 走 `portfolio_handoff`）。这些是"上下文压缩"的路由决策，却以裸数字形式埋在工具函数里，没有任何配置入口和解释。

### 对二开的直接阻碍

你想给状态加一个新字段（比如置信度、持仓建议），必须同时想清楚：写不写双写？`_synchronize_structured_state` 要不要补齐？`_log_state` 要不要记？三个驱动器（见根基 2）各自怎么读？——加一个字段的成本是设计一个字段的三倍。

## 根基 2：三个平行的图执行驱动器

### 现状证据

同一个 LangGraph 引擎，有三套互不相干的启动/驱动代码：

1. **官方驱动**：`TradingAgentsGraph.propagate()`（trading_graph.py:204-254）——invoke 或 stream，带 fallback state、日志、信号提取；
2. **新 CLI 驱动**：`cli/analyze/run_impl.py:209-262` 的 `stream_with_dashboard()`——自己拿着 `graph.graph`、`graph.propagator` 裸跑流循环，为了 Dashboard 边跑边解释 chunk，跑完手动调用**私有方法** `graph._synchronize_structured_state(trace[-1])`（run_impl.py:261）；
3. **旧 CLI 驱动**：`tradingagents/commands/analyze/app.py` 的 `run_analysis()`——又一套自己的执行+展示逻辑。

### 为什么是根基屎

- 三个驱动器意味着**同一段业务逻辑有三份解释代码**：错误恢复（只有 propagate 有 fallback state）、状态补齐（只有 propagate 和新 run_impl 调）、日志（只有 propagate 写）。同一个 bug 在三条路径上表现不同。
- 新 run_impl 直捅图内部（`graph.graph`、`graph.propagator`、私有 `_synchronize_structured_state`），等于把 `TradingAgentsGraph` 的内部结构焊死在 UI 层——你想重命名任何一个内部属性，先炸 UI。
- 这是"UI 直接消费引擎内部状态"的极端形态：连引擎的公开入口都绕过了。

### 对二开的直接阻碍

二开加功能必然要动图（新 agent、新阶段）。三个驱动器意味着每个改动要在三处验证。而且你无法写一个"无 UI 的应用层测试"——因为新 CLI 的执行逻辑和 Rich Dashboard 绑在同一个函数里。

## 根基 3：try/except ImportError 静默换引擎——最危险的一条

### 现状证据

三处完全相同的模式：

- `tradingagents/__main__.py:46-51`：先 import 新 `cli.analyze.app`，捕 `ImportError/AttributeError` 后回退旧 `commands.analyze`；
- `cli/main_menu.py:99-108`（screener）与 `cli/main_menu.py:113-121`（analyzer）：同样模式。

### 为什么这是根基屎

`except ImportError` **分不清"新模块还没写"和"新模块里有 bug"**。你在新 CLI 里改代码，手滑写出一个 ImportError（比如 typo、漏装依赖、循环导入），程序不会报错——它会**安静地切回旧引擎**。你盯着屏幕以为在验证新功能，实际跑的是 500 公里外的旧代码。这类 bug 的排查时间以天计，而且是 vibe coding 的工作方式（大段让 AI 改代码）下**最高概率翻车**的场景。

配套问题：

- `cli/main.py` 自称"DEPRECATED 重定向"，却指向**旧实现** `tradingagents.commands.analyze.app`（cli/main.py:37）——重定向方向就是反的；
- `tradingagents/__main__.py:71-73` 用 `sys.argv = ["screener"] + remaining_args` 篡改全局 argv 来桥接子 typer app——hack 而非集成；
- `cli/main.py:17-34` 在 **import 时**检查依赖并 `sys.exit(1)`——`import cli.main` 这个动作本身能杀掉进程。

### 对二开的直接阻碍

没有可预测的执行路径 = 没有可复现的调试。这是所有问题里**性价比最高**的一个修复：删掉 fallback，让 ImportError 直接炸出来，一天内能做完，之后所有新代码的测试才可信。

## 根基 4：配置双中心 + 全局可变单例

### 现状证据

系统里有**两份并行配置**：

1. **图局部配置**：`TradingAgentsGraph.__init__` 里 `self.config = config or DEFAULT_CONFIG`（trading_graph.py:72）；
2. **数据层全局配置**：`dataflows/config.py:134` 的模块级 `_config` 单例。

两者唯一的同步点是图构造时的一行：`set_config(self.config)`（trading_graph.py:85）——**单向、一次性、浅拷贝**。

由此产生的坑：

- **部分配置 = 崩溃**：`self.config = config or DEFAULT_CONFIG` 不做默认值合并。如果你按 `dataflows/config.py` 文档里示范的方式传 `TradingAgentsGraph(config={"max_debate_rounds": 5})`，下一行 `os.makedirs(self.config["data_cache_dir"])`（trading_graph.py:88）直接 KeyError。文档教的用法本身就是炸的。
- **双实例互相污染**：构造两个图（不同 config），第二个的 `set_config` 覆盖全局 `_config`，第一个图后续的所有数据路由悄悄换成了第二个图的配置。
- **浅拷贝泄漏**：`get_config()` 返回 `_config.copy()`（config.py:242），嵌套 dict（`data_vendors` 等）仍是共享引用——"防止意外修改"的注释承诺的是它做不到的事。
- **图构造器顺便改配置**：`__init__` 里直接往 `self.config["screener_context"]` 写入派生值（trading_graph.py:79-82），配置对象在传递途中被加工。

### 为什么是根基屎

配置是所有模块的公共输入。它一烂，每个模块都要写防御性 `.get()` 默认值（全仓到处都是 `config.get("xxx", 默认值)`，同一默认值在不同文件里重复出现），漂移无法追查。

### 附：`__init__` 的上帝对象化

`TradingAgentsGraph.__init__`（trading_graph.py:56-164）一个构造函数做了 12 件事：校验并**改写**配置、同步全局配置、建目录、建 2 个 LLM client、建 6 个记忆对象、加载历史结论、建 skill injector、建 tool nodes、建条件逻辑、装配图、建 propagator/reflector/signal processor。"构造"和"装配"和"全局副作用"不分家。

## 根基 5：数据层依赖反了 + 环 + 虚构的供应商

### 5.1 反向依赖（通用层 import 应用层）

`dataflows/cn_indicators.py:25`：

```python
from tradingagents.screener.data_access import ScreenerDataAccess
```

`dataflows` 是通用数据层，`screener` 是上层应用——下层 import 上层。且 `cn_indicators.py:60` **每次取行情都新建一个 `ScreenerDataAccess` 实例**：该实例的限流器（`ThrottledRequester`，data_access.py:109）和历史缓存（`_hist_cache`，data_access.py:121，注释自称 "process-level cache"）随实例一起报废——**在这条路径上，限流和缓存形同虚设**。

附带发现：`dataflows/interface.py:134-147` 的 `_call_screener_data_access` / `_screener_callable`（上轮报告点名的反向依赖点）**已经是死代码**——定义了但 `VENDOR_METHODS` 里没有任何条目引用它。上轮报告这一条已过时，但反向依赖本身经 `cn_indicators` 活得好好的。

### 5.2 四模块依赖环（靠延迟导入苟活）

实测导入关系：

```text
dataflows/interface.py:13          → rag（get_cn_news_retriever，try/except 包着）
rag/cn_news_retriever.py:448, 538  → cn_sector_news_tools / news_data_tools（函数内延迟 import）
cn_sector_news_tools.py:27         → dataflows.interface（顶层 import）
news_data_tools.py:19              → dataflows.interface（顶层 import）
```

环：`interface → rag → cn_news_retriever → cn_sector_news_tools → interface`。目前没炸的唯一原因是两条边藏在函数体内、一条边裹在 try/except 里。谁要是哪天顺手把这些提升成顶层 import，直接 ImportError。

### 5.3 "供应商"是命名虚构

`dataflows/interface.py` 维护着一套看起来很专业的供应商体系：`tencent_finance`、`sina_finance`、`ths_data`、`baidu_finance`、`baostock_data`……但看 `VENDOR_METHODS`（interface.py:160-275）的实际接线：

- `tencent_finance.get_stock_data` → `akshare_interface.get_akshare_stock_data`
- `ths_data.get_fundamentals` → `akshare_interface.get_akshare_fundamentals`
- `baidu_finance.get_cn_policy_news` → `akshare_interface.get_akshare_cn_policy_news`
- ……

**几乎所有"供应商"最终都路由进 `akshare_interface.py` 这一个 1619 行的文件**。供应商层是一层命名包装，不是真实的适配器隔离。好处是改动集中，坏处是你以为换了供应商就换了数据源（失败隔离），实际常常还是同一份 akshare 代码换了个入口。

另外 `route_to_vendor()` 里 interface.py:378-387 有一段 alias 换回逻辑：由于 `_attach_legacy_aliases()`（interface.py:278-297）已经把 alias setdefault 成同一个函数对象，这段 `if ... is not impl_func` 的判断**永远不会触发**——又一段死逻辑。

### 5.4 `ScreenerDataAccess` 本体

1,905 行单类，62 个方法（实测 grep），混合：8 个数据源的抓取+解析（`_fetch_hist_sina/_tencent/_tencent_direct/_baostock/_yfinance`、`_fetch_concept_ths`、`_fetch_fund_flow_em`……）、174 行的实时探测（`_run_live_probes`，data_access.py:1256）、能力矩阵构建、请求头伪装（`_maybe_spoof_headers`）、按供应商 sleep（`_sleep_for_vendor`）、探测缓存。**一个类同时因为"供应商变了/解析格式变了/探测策略变了/限流策略变了"四种原因被改。**

## 根基 6：新旧 CLI 分叉 + 安装入口指向旧引擎

（证据已在报告 1 §4.1-4.3 详列，这里讲机理。）

复制型屎山的标准演化：**复制 → 两边都改 → 分叉 → 不知道哪边是对的**。当前四对文件已进入"分叉"阶段（utils.py 差 720 行）。更糟的是环：新层 5 处反向 import 旧层，旧层 0 处引用新层——想删旧层，先要拆掉新层的奶嘴；而新层的奶嘴里有一根是**安装入口**（`pyproject.toml:36` → `cli/main.py` → 旧 app）。

`pyproject.toml:39` 还把 `cli*` 当顶层包发布：site-packages 里出现一个叫 `cli` 的通用包，与任何其他生态工具撞名的风险自负。

## 根基 7：吞异常文化 + 作文注释文化

### 吞异常（171 处 `except Exception`）

几个最伤的样本：

- `trading_graph.py:192-196` `_safe_tools`：工具创建失败 → 静默返回空列表。分析师在无工具状态下跑完，你不会知道；
- `trading_graph.py:452-460`：记忆持久化失败 → `except: pass`，注释还写着"必须永不崩溃"——但连 log 都没有；
- `cli/analyze/run_impl.py:263-265`：最终决策提取失败 → 决策显示 N/A，异常吞掉。

多供应商系统确实需要降级，但当前没有**类型化错误边界**（区分"供应商挂了，换下一个"和"代码 bug，必须炸"），于是所有失败都长一个样：安静。

### 作文注释（vibe coding 的化石层）

`dataflows/config.py` 是标本：368 行里约 40 行是代码，其余是 ASCII 框图画出的"详解"、设计模式分析（自称用了单例+代理+模板方法+备忘录模式）。同类化石分布在 `agent_states.py`（287 行里约 60 行代码）、`aggressive_debater.py` 等。这些注释不是给读者的，是当时 AI 生成的"作文"，**它们会随代码演化失真**（config.py 的作文里示范的用法本身就是会 KeyError 的用法，见根基 4）。

### 调试打印残留

`cli/analyze/run_impl.py` 里 6 处 `print("[DEBUG] Step N...")` 直接混在生产路径。

## 七条根基的依赖关系（为什么按这个顺序拆）

```text
根基3 (ImportError静默换引擎) ──不拆，你无法确认任何重构的验证结果
   │
根基6 (双CLI分叉) ──不拆，每次修 bug 要修两处；安装入口还指着旧的
   │
根基2 (三驱动器) ──不拆，图的任何改动要在三处同步
   │
根基1 (状态双写) ──不拆，加字段成本×3；拆了它，事件/UI/报告层才有稳定契约
   │
根基4 (配置双中心) ──不拆，数据层重构没有稳定的输入
   │
根基5 (数据层反向+环) ──最难，放最后；但它不阻塞前三步
```

**根基 3 → 6 → 2 是一条线（入口与执行收口），根基 1 → 4 是第二条线（契约收口），根基 5 是第三条线（数据层）。** 三条线不必同时动，但每条线内部有先后。

具体执行顺序、每步验收标准见报告 3。
