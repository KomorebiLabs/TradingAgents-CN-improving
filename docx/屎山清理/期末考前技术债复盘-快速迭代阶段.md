## 一、先把话说清楚：屎山快速迭代过程（2026-06）

这份文档记录的是一段典型的快速迭代过程：功能要先跑起来，数据供应商要先接通，分析链路要先闭环，CLI、主 LangGraph 链和 Screener 要先能够被真实调用。这样的阶段有一个很现实的特点：当下的优先级是“让系统继续向前走”，而不是一次性把所有边界、抽象、异常分类、测试隔离和文档治理都做到最终形态。

于是，经过Phase 2026-05 and 2026-06 项目开发后留下了一批后来必须偿还的技术债：重复实现逐渐分叉，数据供应商逻辑过度集中，异常被过宽地捕获，旧入口与新入口并存，状态字段存在双写，真实数据源的接口漂移没有统一护栏，测试数量与真实运行能力之间也一度不匹配。

准确的说法是：在快速交付约束下，部分临时决策没有及时转化为长期结构；而一旦系统继续叠加功能，临时决策就会变成维护成本。

本项目后续的治理工作，价值不只在于“删了多少文件”或“通过了多少测试”，而在于把这些隐性成本逐步变成可观察、可讨论、可验证的工程问题。

## 二、反思：问题是怎样形成的（Phase 2026-06）

### 2.1 功能优先导致边界后置

早期快速迭代最容易出现的路径是：

```text
需求出现
  ↓
先接入一个数据源或一个调用入口
  ↓
先让主流程跑通
  ↓
遇到异常就局部兜底
  ↓
为了兼容旧调用方保留旧实现
  ↓
新功能继续叠加
  ↓
临时方案变成系统边界
```

这条路径短期有效，长期却会产生几个连锁反应：

1. 数据访问、解析、缓存、限流和供应商探测容易被塞进同一个类；
2. 新 CLI 为了快速上线，可能与旧 CLI 并行存在；
3. 图执行逻辑、仪表盘展示和命令行状态处理可能各自维护一套路径；
4. 异常处理优先追求“不阻断流程”，久而久之就变成“看不见失败”；
5. 测试首先覆盖能否导入和能否运行，契约测试、真实供应商探测和质量评估则被推迟。

### 2.2 个人项目中的现实约束

这是一个个人维护项目，开发过程需要同时处理功能实现、数据源调研、模型接入、测试、文档和学习任务。快速迭代阶段的时间通常被切成许多小块，工程取舍难以像成熟团队那样一次性完成完整的设计评审、实现、灰度和回滚流程。

因此，早期代码中出现“先写出来、后面再收口”的痕迹并不意外。真正需要复盘的是：

- 哪些临时方案后来变成了稳定依赖；
- 哪些异常处理掩盖了数据不可用；
- 哪些兼容层已经没有真实调用者；
- 哪些测试只证明了离线 stub 能运行，却没有证明真实运行可用；
- 哪些文档记录了内部情绪，却没有转换成面向维护者的工程信息。

### 2.3 “能运行”不等于“可维护”

快速迭代阶段最容易把以下几种状态混为一谈：

| 状态 | 实际含义 | 不能推出的结论 |
|---|---|---|
| 可以导入 | 模块语法和部分依赖没有立即阻断导入 | 不能推出真实 API 可用 |
| 离线测试通过 | stub、mock 或纯函数行为符合预期 | 不能推出生产供应商稳定 |
| CLI 能启动 | 入口注册和参数解析基本存在 | 不能推出整条分析链有有效数据 |
| 模型返回文本 | 请求到达模型并获得响应 | 不能推出决策证据充分 |
| 结果对象生成 | 流程完成了结构化输出 | 不能推出结果值得信任 |

后续治理的核心，就是把这些状态拆开测量，而不是用一个“成功/失败”标签覆盖所有问题。

## 三、期末考试前的历史技术债清单（屎山！！！！）

下面的清单来自历史审阅材料，描述的是治理开始前后被确认的问题类型。

### 3.1 入口与重复实现债

历史上同时存在新旧 CLI、旧命令层和新命令层，部分文件曾经复制后各自演化。复制最初可能是为了快速试验或兼容迁移，但只要两份实现继续被修改，就会出现：

- 一个入口已经修复，另一个入口仍保留旧行为；
- 配置项在两个路径上的默认值不一致；
- 统计、报告和工具装配逻辑出现分叉；
- 维护者无法仅凭文件名判断哪个实现是权威实现。

治理原则是：先通过调用关系确认真实入口，再让旧层变成明确的薄转发或安全退役，不能只凭文件名猜测并删除。

### 3.2 数据访问集中化债

历史 `ScreenerDataAccess` 体量过大，承担了供应商注册、请求、解析、缓存、探测、能力矩阵、限流和反爬兼容等多种职责。这样的设计在接入少量数据源时很快，但随着接口漂移和降级策略增加，任何一处修改都可能影响多个无关能力。

后续拆分的方向是：

```text
供应商选择
  ├─ 能力与健康状态
  ├─ 请求与重试策略
  ├─ 响应解析
  ├─ 缓存与限流
  └─ 领域数据端口
```

拆分的目标不是为了追求文件数量，而是让“供应商不可用”“响应格式变化”“领域数据缺失”和“调用方降级”能够分别测试和定位。

### 3.3 异常可见性债

宽泛的 `except Exception` 在快速迭代阶段常被用来避免单个数据源或单个分析步骤阻断整条链路。但如果异常被直接转换为 `None`、空列表或通用 unavailable，调用方就无法区分：

- 供应商暂时超时；
- API 鉴权失败；
- 返回结构变化；
- 当前市场确实没有数据；
- 解析器存在 bug；
- 请求参数不符合供应商要求。

后续的改进方向不是简单地“所有异常都抛出去”，而是建立分类错误边界，并在降级结果中保留来源、原因、时间和下一步建议。

### 3.4 状态契约债

主链曾经同时维护结构化状态和平铺展示字段。双写在迁移期可以降低改造阻力，但如果没有明确 canonical 字段，最终会出现：

- 一个字段已更新，另一个字段没有同步；
- UI 读取到了旧值；
- 测试只覆盖其中一套字段；
- 新开发者不知道应该写哪一个字段。

解决方式是明确权威状态、兼容读取范围和退役时间表，并用契约测试阻止平铺字段无计划回流。

### 3.5 真实数据与离线测试之间的债

离线测试的价值是稳定验证核心逻辑，但它无法代替真实供应商验收。尤其是金融数据场景，接口字段、交易日、股票代码格式、反爬策略和数据可用窗口都会变化。

因此，后续需要把验证分层：

| 验证层 | 目标 |
|---|---|
| 单元测试 | 纯函数、解析器和边界条件 |
| 契约测试 | 供应商响应形状和错误映射 |
| 离线集成测试 | 主链路编排和状态转换 |
| 真实探测 | 当前 API、凭据、网络和接口漂移 |
| 真实业务验收 | 数据是否足够支撑推荐或分析结论 |

### 3.6 文档治理债

开发过程中产生的内部清单、审阅草稿、重构日志和面试准备材料，目的不同、语气不同、读者也不同。如果全部直接放在公开仓库，维护者、用户和面试官很难判断：

- 哪些是最终结论；
- 哪些是当时的假设；
- 哪些是已经解决的问题；
- 哪些只是暂存的想法；
- 哪些内容仅适合个人备忘，不适合公开展示。

这次文档整理的目标，是把“内部工作痕迹”转化为“可复盘的工程材料”，而不是删除所有不完美的历史。

## 四、暑假后续治理是怎样展开的

### 4.1 先建立基线，再动代码

历史审阅没有一开始就对整个仓库进行无差别重写，而是先确认：

1. 当前入口有哪些；
2. 哪些文件仍被真实引用；
3. 哪些问题是结构性问题，哪些只是文档或缓存残留；
4. 哪些修改会影响主 LangGraph 链；
5. 哪些 Screener 供应商问题能够被离线复现；
6. 哪些结论需要真实 API 才能验证。

这种顺序很重要。没有基线的重构，很容易把“旧代码不好看”误判成“旧代码一定没有调用者”。

### 4.2 先收入口，再统一执行路径

入口治理的重点不是把旧文件全部删掉，而是确认安装入口、模块入口、Analyzer 入口和 Screener 入口是否指向同一套核心能力。完成入口收口后，主图执行逐步统一到流式执行驱动，CLI 和官方调用路径共享同一条内核，减少“命令行能跑、库调用却是另一套逻辑”的风险。

### 4.3 再建立契约和测试护栏

测试护栏覆盖的重点包括：

- 关键模块导入没有静默副作用；
- 版本号只有一个来源；
- 状态压缩与交接阈值稳定；
- 供应商路由的别名和优先级可预测；
- 图流式执行的正常、异常和 fallback 路径可验证；
- 全部活跃 Python 文件可编译；
- 分析请求、结果和执行事件具备明确契约。

这些测试不是为了证明“系统已经没有问题”，而是为了防止已经解决的问题重新回流。

### 4.4 最后补真实运行和数据证据

Screener 的治理进一步关注了离线测试无法发现的问题：

- 数据供应商接口漂移；
- 新闻或财务数据无返回；
- A 股代码、日期和交易日处理不一致；
- 推荐依据不足但仍然输出强结论；
- DeepAnalyzer 实际没有执行或执行状态不透明；
- 供应商失败后没有留下可解释的健康状态。

治理后的结果应该能够回答三个问题：

1. 这条数据来自哪里？
2. 这条数据是什么时间获取的？
3. 数据不足时，系统为什么降级，以及用户应该怎样理解结论？

## 五、对“快速迭代阶段的我/Agent”的客观评价：菜就多练，输不起就别玩

### 5.1 当时做对了什么

- 把主流程和数据源先连接起来，验证了产品方向不是停留在设计稿；
- 在多供应商环境下保留了继续扩展的空间；
- 通过 CLI、LangGraph 和 Screener 形成了可操作入口；
- 在发现真实运行与离线测试不一致后，继续补充健康状态、证据门禁和真实验收；
- 没有把历史问题完全掩盖，而是建立了报告、路线和施工记录。

### 5.2 当时留下了什么

- 对旧入口和新入口的边界判断不够早；
- 对异常的分类和可观测性投入不足；
- 数据供应商适配逻辑过度集中；
- 测试数量曾经不能代表真实业务可用性；
- 文档面向内部自检，公开表达不够克制；
- 部分兼容方案没有在设计之初写明退役条件。

### 5.3 现在应该怎样评价

不应该用“当时写得很烂”结束复盘，也不应该用“后来全部修好了”替代证据。更准确的评价是：

> 这是一个先完成端到端闭环、再通过系统审计偿还技术债的项目。快速迭代阶段留下了结构和可观测性问题，但后续治理把这些问题转化成了入口收口、契约测试、供应商健康、证据门禁、真实验收和文档治理等可验证工作。

这段经历的工程价值，恰恰在于看到了“能跑”的边界，并且补上了从“能跑”到“可维护、可解释、可验收”之间的缺口。

## 六、未来维护者的接力清单

后续维护不应重新回到“先接入、后解释、最后再补测试”的循环。每次新增能力至少应完成以下检查：

### 6.1 新增数据供应商

- 明确能力范围和不支持的市场；
- 提供字段映射和响应样例；
- 区分认证失败、限流、超时、空数据和结构漂移；
- 接入统一健康状态；
- 增加离线解析测试；
- 增加可选真实探测；
- 在用户结果中披露数据来源和时间。

### 6.2 修改主 LangGraph 链

- 先确认状态字段的 canonical 方向；
- 不在 UI 层复制图执行逻辑；
- 不以宽泛异常吞掉关键节点失败；
- 增加正常、部分失败和完全失败路径测试；
- 记录 token、耗时、模型和工具调用证据；
- 真实运行前先做小样本、低成本验收。

### 6.3 修改 Screener 推荐逻辑

- 明确候选池、过滤条件和排序权重；
- 防止缺失数据被当成零分或正向信号；
- 区分“暂无推荐”和“推荐信号弱”；
- 对推荐结论设置证据门槛；
- 用时间点数据避免未来信息泄漏；
- 将回测、样本外验证与真实推荐分开报告。

### 6.4 新增公开文档

- 先判断它是最终文档、历史复盘还是个人草稿；
- 对外使用中性、可验证的标题；
- 保留真实时间口径；
- 不把内部玩笑、情绪化表达和面试脚本放入公开仓库；
- 写清楚已完成、未完成和需要真实环境验证的边界。

## 结语

快速迭代本身不是问题。真正危险的是快速迭代之后，项目仍然假装没有发生过临时决策，也没有为这些决策建立回收机制。

本项目的历史技术债提醒未来维护者：

- 先跑通可以，但要留下回收清单；
- 可以降级，但不能让降级结果伪装成成功；
- 可以兼容旧入口，但要记录真实调用者和退役条件；
- 可以用 mock 保证离线稳定，但要把真实探测单独纳入验收；
- 可以在压力下做取舍，但事后必须用证据复盘取舍的后果。

所谓“整理过往文档”，最终不是把过去包装得更漂亮，而是把过去的工程选择讲清楚，让下一个维护者知道：哪些地方曾经是临时方案，哪些地方已经被治理，哪些地方仍然值得继续投入。
